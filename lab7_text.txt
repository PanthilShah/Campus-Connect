1. Objective

Lab 6 decomposed the backend into three independently runnable microservices - User, Product and Order -
communicating directly over a Docker network, with the API Gateway introduced only as a concept. This lab makes
that concept real: build an actual API Gateway as the single entry point for clients, make the gateway's knowledge
of service locations configurable rather than hard-coded (a lightweight form of service discovery), and finally
deploy the containerized system to the cloud so it is reachable over the internet, not just localhost.

Full-stack flow for this lab:
Client / Postman  ﬁ  API Gateway (public, cloud-hosted)  ﬁ  Service Registry / Config  ﬁ  User / Product / Order
Services (containers)  ﬁ  MongoDB Atlas

2. Part A - Build a Real API Gateway

Replace direct client-to-service calls with a single gateway entry point. The gateway contains no business logic - it
only routes requests and handles cross-cutting concerns.

(cid:127) Create a new api-gateway service in the same tech stack as your Lab 6 services (e.g. Express +

http-proxy-middleware, or the Spring Boot / Node equivalent you used).

(cid:127) Route incoming paths to the correct backend service: /users/* ﬁ User Service, /products/* ﬁ Product Service,

/orders/* ﬁ Order Service.
Add a gateway health-check endpoint, e.g. GET /health, that reports the gateway is running.

Add basic request logging at the gateway (method, path, target service, response status).

Add centralized error handling: if a target service is unreachable, the gateway returns a clear 502/503 response
instead of hanging or crashing.

(cid:127) Only the gateway's port should be exposed externally in Docker Compose - User, Product and Order should be

reachable only from inside the Docker network, not directly from outside.

Discussion question (answer briefly in your README): Why introduce an API Gateway instead of letting
clients call each service directly? Think about a single entry point, hiding internal structure, and centralizing
concerns like logging and error handling.

3. Part B - Service Discovery (Configuration-Based)

The gateway must not hard-code service locations inside route-handling code. Externalize them into configuration so
locations can change without touching application code - this is the lightweight, practical form of service discovery for
this lab.

(cid:127) Define a small service registry as environment variables or a config file, e.g.: USER_SERVICE_URL,

PRODUCT_SERVICE_URL, ORDER_SERVICE_URL.

The gateway reads this configuration at startup and uses it to build its routing table - route definitions should
reference the config values, not literal hard-coded URLs.

Prove it works: change a service's URL/port only via configuration (no code change) and confirm the gateway
routes correctly to the new location.

In your README, briefly contrast this static/config-based approach with dynamic service discovery (e.g. Consul,
Eureka, Kubernetes DNS) - what would a dynamic registry add that a static config file cannot?

9. Learning Outcomes

By the end of this lab, students will be able to: explain why an API Gateway is used as a single entry point in a
microservices system; implement gateway routing, logging and centralized error handling; externalize service
locations into configuration as a lightweight form of service discovery, and explain how this differs from dynamic
service discovery; and deploy a containerized multi-service application to a cloud platform so it is reachable over the
internet.
